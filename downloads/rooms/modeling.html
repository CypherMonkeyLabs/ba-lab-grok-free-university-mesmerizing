Modeling

BPMN, UML, ERD, and C4 in plain language.

  • Pick the question before the notation. BPMN is for flow: events, activities, gateways. UML is a family of sketches. An ERD names things and relationships. C4 steps from system context to container, component, and code. Stop at the level the audience can use. Draw the unhappy path.
  • Start: a return arrives. Activity: look up the order. Gateway: is the item within the stated window? Yes path: refund. No path: explain the window and stop.
  • Both paths have an end. The window length is a business rule beside the drawing, so a policy change does not redraw the map.
  • BPMN in brief. Object Management Group publishes BPMN 2.0. For study, learn events, activities, gateways, and sequence flow. A gateway is a decision, not a task. Label the outgoing paths with conditions a stranger can test.
  • Current state, then future. Draw how the work happens this week, including the spreadsheet and the rework. Then draw the proposed state. If you only draw the future, you will miss the step that actually takes the time.
  • UML, used sparingly. OMG publishes UML. Use the diagram that answers the question in the room. A use case diagram shows who wants what. An activity diagram shows flow. A sequence diagram shows messages over time. A class diagram shows structure. One diagram, one question.
  • Entity relationships. An entity is a thing you store. A relationship states how many of one relate to how many of another. Name the relationship from both directions. 'Customer places order' is clearer than a line with no verb.
  • C4, four levels. The C4 model site describes four abstractions: software system, container, component, and code. Start with a system context diagram: the system, the people, and the other systems. Go deeper only where the audience needs it.
  • SIPOC. Supplier, input, process, output, customer is a one-page boundary. It is enough to see whether you are looking at the right process before you draw thirty boxes. This is a study scaffold, not a claimed standard text.
  • States. State models help when a thing has a life: draft, submitted, approved, rejected. Name the event that causes each move and who may cause it. The technique list includes state modelling.
  • Decisions apart from flow. If a gateway contains a policy, lift the policy into a decision with inputs and outputs. The process then stays stable when the policy changes. Decision modelling is on the technique list.
  • Interfaces. Interface analysis asks what crosses a boundary: data, a document, or a handoff. For each crossing, name the producer, the consumer, the trigger, and what happens when it fails.
  • Story map. A story map places user activities across the top and breaks releases downward. The first horizontal slice should be a thin outcome someone can use, not a layer of database tables.
