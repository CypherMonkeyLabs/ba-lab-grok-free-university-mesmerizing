  • A generic retailer asks for WhatsApp. Foundations asks for the need. The omnichannel room asks which actor and which context must move. The metrics room asks which formula will show that the move helped. The migration room asks who signs the operating model.
  • The feature overview names Salesforce, Zendesk, and ServiceNow as CRM examples a profile can combine with contact history. That is a citation. It is not a selection. Anything the pages did not describe stays off the map.
  • Where the practice sits. Business analysis touches product ownership, project delivery, process improvement, data analysis, architecture, and change management. The BABOK Guide is the core reference in this lab. Neighboring guides are cited only where a page opened.
  • Sister roles. Product manager, product owner, project manager, process analyst, data analyst, business architect, and quality analyst share techniques with business analysis. Ask which decisions each role owns on this initiative. Shared techniques do not mean shared authority.
  • Bridges to other labs. The omnichannel, metrics, and migration rooms use the same elicitation and acceptance habits as the rest of this lab, plus queue, channel, and quality measures from pages that opened. AI agent work needs a human review step on any requirement the model drafted. This lab links those topics. It does not claim a vendor implementation.
  • Future hooks. Useful next studies are decision modeling, process mining, and evaluation of AI-assisted analysis. Each is introduced here only as far as a public source opened. Deeper vendor features stay marked to be confirmed.

Each line names the page that was opened. A word that is not in that list is not defined here.
  • Mind map. Read the ecosystem drawing as a study map, not as a vendor architecture. The person and the goal sit in the middle. Around them: the channels, the journey and the blueprint, the queue and the flow, the agent and the customer profile, the measures, and the three migration workstreams. If a box has no opened source, it does not belong on the map.
  • Sister technologies. The feature overview describes neighboring pieces a contact-center analyst will meet. Conversational IVR and chatbots can use Amazon Lex. Customer Profiles can combine contact history with a CRM; the page names Salesforce, Zendesk, and ServiceNow. Forecasting and agent scheduling are described for the workforce team. Screen recordings are described as a way to review what an agent did. Contact flows can call AWS Lambda, including toward a CRM. Email on that page is tied to Amazon Simple Email Service. Naming a product here is a citation, not a recommendation.
  • Integration map. A study sequence, taken from how the feature overview lays the work out, is: channel, then contact flow, then queue, then agent workspace, with a customer profile beside the agent and a case when the issue spans contacts. The WhatsApp page adds a step in front of that sequence: a business account and a verified number before any message arrives. Draw only the arrows you can name. An unnamed arrow is a gap.
  • Bridges into the other rooms. Use Foundations for the need before the platform name. Use Requirements for the handoff and the acceptance scenario. Use Modeling when the journey or the blueprint needs a picture. Use the metrics room when a chart needs a formula. Use Domains for the contact-center lens beside other industries. Use the migration room when the change is a move from a legacy platform. Shared pages do not merge the decision rights.
  • Future hooks that a page actually describes. The feature overview describes generative AI agent assist during calls and chats, generated post-contact summaries, and forecasting and scheduling. Those are descriptions of a product page, not a claim that a reader's platform has them, and not a roadmap. A person still accepts any requirement a model drafts. The WhatsApp setup page adds a planning constraint you can write today: business verification can take up to 2 weeks. Features this check did not open stay unmarked.
